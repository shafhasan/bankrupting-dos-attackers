# Synthetic Poisson LINEAR Experiment

This repository runs a synthetic traffic experiment for the LINEAR pricing algorithm. Good flows are generated by a homogeneous Poisson process, while malicious flows can follow constant, Poisson, or concentrated burst arrival patterns.

The implementation uses fixed mathematical iteration boundaries, records empty iterations, calculates Pearson correlation from every processed flow, and plots the raw curves at configurable checkpoints. It does not apply scaling or normalization and does not calculate RMSE.

## Repository contents

```text
.
├── Dockerfile
├── docker-compose.yml
├── requirements.txt
├── poisson_linear_experiment.py
└── results/                         # Created when an experiment is run
```

## Requirements

Install one of the following:

- Docker Desktop on Windows or macOS.
- Docker Engine with the Compose plugin on Linux.

No local Python installation is required when using Docker.

## Build the Docker image

Run the following command from the directory containing the `Dockerfile`:

```bash
docker build -t poisson-linear-experiment:latest .
```

Rebuild the image whenever the Python script, Dockerfile, or dependency versions change:

```bash
docker build --no-cache -t poisson-linear-experiment:latest .
```

## Quick start with Docker Compose

The default Compose configuration runs 100,000 flows with constant malicious traffic, a good-flow rate of 15 flows/s, and seed 42:

```bash
docker compose up --build
```

Results are written to:

```text
results/100k_constant/
```

Because this is a finite batch experiment, the container exits after producing the result files.

## Run with Docker on macOS or Linux

Create the results directory:

```bash
mkdir -p results
```

### 100,000 flows with constant malicious traffic

```bash
docker run --rm \
  --mount type=bind,source="$(pwd)/results",target=/results \
  poisson-linear-experiment:latest \
  --total-flows 100000 \
  --good-fraction 0.20 \
  --good-rate 15 \
```

## Command-line parameters

| Parameter | Default | Description |
|---|---:|---|
| `--total-flows` | `1000000` | Total number of generated good and bad flows. |
| `--good-fraction` | `0.20` | Fraction of all flows labeled good. Must be strictly between 0 and 1. |
| `--good-rate` | `100.0` | True Poisson generation rate for good flows, in flows/s. |
| `--bad-pattern` | `poisson` | Malicious arrival pattern: `constant`, `poisson`, or `burst`. |
| `--burst-size` | `500` | Number of bad flows placed in each concentrated burst. |
| `--checkpoint-step` | `100` | Save and plot one checkpoint after every specified number of flows. |
| `--x-log-threshold` | `100000` | Use a logarithmic x-axis when the largest checkpoint exceeds this value. |
| `--y-log-threshold` | `100` | Retained for command-line compatibility; both linear-y and log-y plots are generated. |
| `--seed` | `42` | NumPy random seed used for reproducibility. |
| `--output-dir` | `poisson_linear_results` | Directory that receives all generated outputs. Inside Docker, use a path under `/results`. |

## Traffic generation

Let the total number of flows be \(N\) and the configured good fraction be \(f_g\). The number of good flows is

$$
N_g = \mathrm{round}(Nf_g),
$$

and the number of malicious flows is

$$
N_b = N-N_g.
$$

### Good traffic

Good-flow inter-arrival times are sampled independently from an exponential distribution:

$$
X_i \sim \mathrm{Exponential}(\lambda_g),
$$

where `--good-rate` supplies \(\lambda_g\). Cumulative sums of these inter-arrival times produce a homogeneous Poisson arrival process.

### Constant malicious traffic

The \(N_b\) malicious timestamps are evenly spaced over the duration of the generated good trace. Their approximate rate is

$$
\lambda_b \approx \frac{N_b}{T},
$$

where \(T\) is the good-trace duration.

### Poisson malicious traffic

Malicious inter-arrival times are exponential with rate

$$
\lambda_b = \frac{N_b}{T}.
$$

The malicious process is generated independently of the good process.

### Concentrated burst traffic

All malicious flows are placed inside bursts. No malicious background traffic is generated outside the bursts. The number of bursts is

$$
K = \left\lceil \frac{N_b}{S_b} \right\rceil,
$$

where \(S_b\) is `--burst-size`. Burst centers are spaced uniformly over the trace duration. A very small nonnegative jitter orders flows within each burst while keeping them effectively simultaneous.

## Good-rate estimation and iteration boundaries

The supplied `--good-rate` controls good-traffic generation. After generation, the experiment estimates the good rate from all positive good-flow inter-arrival times:

$$
\widehat{\lambda}_g = \frac{1}{\overline{X}},
$$

where \(\overline{X}\) is their sample mean. LINEAR then uses the fixed iteration length

$$
L = \frac{1}{\widehat{\lambda}_g}.
$$

The first merged-flow timestamp anchors the mathematical boundary grid. Iterations are half-open intervals:

$$
[t_k,t_{k+1}).
$$

A flow exactly on a boundary belongs to the new iteration. If a gap crosses multiple boundaries, every intervening interval is recorded, including completely empty intervals.

This is an offline synthetic experiment: known-good timestamps are used to estimate \(\widehat{\lambda}_g\), after which the estimate is frozen and all chronologically merged flows are replayed.

## LINEAR pricing and costs

Pricing is label-blind. If \(s\) flows have already been serviced in the current iteration, the arriving flow receives price

$$
p=s+1.
$$

Labels are consulted only after assigning the price, for evaluation. The algorithm cost is

$$
A=N_{\mathrm{serviced}}+\sum_{j\in\mathcal{G}}p_j,
$$

where the first term is one unit of service cost per flow and \(\mathcal{G}\) is the set of good flows. The adversary cost is

$$
B=\sum_{j\in\mathcal{B}}p_j,
$$

where \(\mathcal{B}\) is the set of malicious flows. The empirical performance curve is

$$
R_n=\frac{B_n}{A_n}.
$$

## Theoretical curve and Pearson correlation

The raw Theorem 1 proxy plotted after checkpoint \(n\) is

$$
T_n=\frac{B_n}{\sqrt{B_n(g_n+1)}+(g_n+1)},
$$

where \(g_n\) is the cumulative number of good flows.

The script does not scale or normalize either curve. Pearson correlation is calculated from the paired raw empirical and theoretical values after every processed flow:

$$
r=\frac{\sum_{n=1}^{N}(R_n-\overline{R})(T_n-\overline{T})}{\sqrt{\sum_{n=1}^{N}(R_n-\overline{R})^2}\sqrt{\sum_{n=1}^{N}(T_n-\overline{T})^2}}.
$$

`--checkpoint-step` affects only CSV sampling and plot density. For example, `--checkpoint-step 100` plots every 100 flows, but Pearson still uses all \(N\) flow-level pairs. The Pearson value appears in the plot legend and in `summary.json`.

Because both curves are cumulative, consecutive points are serially dependent. Pearson \(r\) is therefore a descriptive measure of curve-shape agreement, not an inference based on \(N\) independent observations. No Pearson p-value is reported.

## Output files

Each run creates the following files in its selected output directory:

| File | Contents |
|---|---|
| `linear_performance.png` | Raw empirical and theoretical curves on a linear y-axis. The x-axis becomes logarithmic when the configured threshold is exceeded. |
| `linear_performance_log.png` | The same raw curves on a logarithmic y-axis. Nonpositive values are omitted because a logarithmic axis cannot display them. |
| `linear_checkpoints.csv` | Sampled cumulative flows, good-flow count, \(A\), \(B\), \(B/A\), and the raw theoretical proxy. |
| `iteration_composition.csv` | Every mathematical interval, including good, bad, bad-only, and completely empty iterations. |
| `summary.json` | Configuration, generated traffic counts, estimated rate, final costs, iteration statistics, and all-flow Pearson correlation. |

## Verify a run

Open `summary.json` and verify the configuration before comparing plots. For constant traffic, the generated section should report zero burst flows. For burst traffic, it should report zero background bad flows.

For a 100,000-flow run with a 20% good fraction and burst size 500, the expected traffic counts are:

```text
number_good:          20000
number_bad:           80000
number_burst_bad:     80000
number_background_bad:    0
number_bursts:          160
```

Always use separate output directories for constant and burst runs. Reusing an output directory overwrites files with the same names.
